# 迭代记录：eval 是怎么帮我把 Agent 挖出来的

这份记录想说明一件事：**评测的价值不在于最后那个分数，而在于它能逼你把"以为能跑"的东西真正跑一遍**。

这次迭代里，一个我以为早就完工的 Agent，第一次认真跑 eval 时拿了 **0.47/10**。

---

## 背景

W5 是给 Agent 套质量护栏的工程（LLM-as-judge 自动打分 + 自建 Tracer 可观测）。
在给它补录屏素材之前，我打算跑一次 `npm run eval` 拿到一份真实报告。

结果它**从来就没真正跑通过**。

---

## v1 · 基线：0.47/10，工具调用 0 次

[完整报告](./eval-v1-baseline.md)

```
通过率 0% · 加权均分 0.47/10
calc-1  ❌  工具调用 0 次
rag-1   ❌  工具调用 0 次
multi-1 ❌  工具调用 0 次
```

judge 给的理由很关键：*"Agent 实际未调用 calculator 工具，只输出了一条未执行的指令。"*

也就是说模型**知道**该调工具、也**写对**了 JSON，但输出在了正文里，而不是 `tool_calls` 通道。

排查下来是两个叠加的原因：

### 原因 1：`.env` 从来没被加载

`npm start` 走 `index.ts`，`npm run eval` 走 `src/cli.ts` —— **两个入口**。
`dotenv/config` 只写在 `index.ts` 里，于是 `npm run eval` 这条路径上所有环境变量都是 `undefined`，
`AI_MODEL` 静默回落到代码里的硬编码默认值，连到了完全错误的端点。

```ts
// src/model.ts 修复前
export const model = provider.chat(process.env.AI_MODEL ?? 'deepseek-chat');
//                                  ↑ undefined 时静默用错模型，极难发现
```

修法是把加载下沉到 `model.ts`（任何 import 链经过它的入口都会自动加载），
并在环境变量缺失时打印明确告警。

> 顺带一个教训：**不要给关键配置写"看起来合理"的 fallback**。
> 它会把"配置没生效"伪装成"模型不好用"，排查方向直接跑偏。

### 原因 2：模型选错了

修好 env 后仍然全挂。直接拿两个本地模型做对照：

| 模型 | tool_choice=auto | tool_choice=required |
|---|---|---|
| `qwen3:14b` | ✅ 正常返回 `tool_calls` | ✅ 正常 |
| `qwen2.5-coder:14b` | ❌ 只输出 JSON 文本 | ❌ 只输出 JSON 文本 |

`qwen2.5-coder:14b` 在 Ollama 的 OpenAI 兼容端点下**根本不产生 `tool_calls`**。
它懂格式，但把调用写成了正文文本，Ollama 不会去解析。

这个缺陷之所以一直藏着，正是因为原因 1 —— eval 压根没跑通过，自然没人发现。

---

## v2 · 换模型：100% / 9.6 分

[完整报告](./eval-v2-model-fix.md)

只改了 `.env` 里一行 `AI_MODEL`，全部用例通过。

但看 trace 时间线时注意到一件事 —— **每个用例都多出一个 `agent:synthesize` span**：

```
eval:calc-1 ── agent:run ── agent:synthesize   ← 这个是什么？
```

`synthesize` 是我写的一段兜底逻辑：模型在工具调用后没生成文本时，
再补一次 `generateText` 让它基于工具结果合成答案。它一直在被触发，
说明**模型从来没有真正跑完过多步循环**。

顺着这条线索发现了第三个 bug。

---

## v3 · 补 stopWhen：分数没变，但结构对了

`streamText` 缺 `stopWhen`。AI SDK v5+ 默认只跑一步 —— 模型一返回工具调用就结束。

```ts
// src/agent.ts 修复
stopWhen: stepCountIs(5),
```

加完再跑，`agent:synthesize` **消失了**：模型自己跑完循环并输出最终答案，不再需要兜底。

有意思的是**分数几乎没变**（9.6 → 9.4，还低了一点，落在噪声范围内）。
也就是说：**单看分数，v2 和 v3 完全分不出来；看 trace，二者是两回事**。

这正是 W5 想说的事：

> **eval 告诉你"好不好"，可观测告诉你"为什么"。**

缺了后者，v2 那种"分数很好但靠兜底撑着"的状态会一直被当作正常。

---

## v4 · 修 judge：当评测标准本身有问题

v3 里 `rag-1` 的"调用检索"只拿了 6 分，理由是：
*"输出内容未明确体现对检索到的 RAG 片段的具体引用。"*

可 Agent **确实调用了** `searchDocs`（trace 里工具调用 1 次）。

问题出在 judge 身上：我把"是否调用工具"这条**行为标准**，
让它从输出文本里去推断，于是被评成了**输出质量标准**。
评审员看到答案里没有显式引用片段，就判定"没检索"。

修法是给 judge 的 system prompt 加一条判定规则：

```
当评审标准是在问「是否调用了某工具 / 某个行为是否发生时，
必须以下面给出的「实际调用记录」为唯一事实依据，
不要因为输出文本里没提到就判定未调用。
```

改完只跑 `rag-1` 一个用例验证（CLI 此时已支持 `--case` 过滤，单用例 ~2 分钟，全量要 7 分钟）：

```
改前：rag-1  8.2 ❌  调用检索 6/10  "输出未明确体现对检索片段的引用"
改后：rag-1  9.0 ✅  调用检索 8/10
```

**v4 全量：[100% / 9.67](./eval-v4-judge-fix.md)**

```
calc-1  10   ✅  工具调用 1 次
rag-1    9.4 ✅  工具调用 1 次   （调用检索 6 → 9 分）
multi-1  9.6 ✅  工具调用 2 次   （真多步，非并行一次发出）
```

三轮之中最高分，且 trace 里三个用例都只有 `agent:run` —— 无 `synthesize` 兜底。
**分数和架构同时到位**。

## 四轮对比

| 轮次 | 改动 | 通过率 | 加权均分 | `synthesize` 兜底 | 根因 |
|---|---|---|---|---|---|
| [v1](./eval-v1-baseline.md) | 基线 | 0% | 0.47/10 | 未触发（压根没调工具） | env 未加载 + 模型不支持 tool_calls |
| [v2](./eval-v2-model-fix.md) | 换 `qwen3:14b` | 100% | 9.6/10 | **每个用例都触发** | 缺 `stopWhen`，靠兜底补答案 |
| [v3](./eval-v3-stopwhen.md) | 补 `stopWhen` | 67% | 9.4/10 | 消失 ✅ | judge 标准不可判定 |
| [v4](./eval-v4-judge-fix.md) | 修 judge 判定依据 | **100%** | **9.67/10** | 消失 ✅ | — |

四次改动，**没有一次是改 prompt**。全部是配置、框架用法、评测设计层面的问题 ——
也全部是"只看代码不会发现、一跑就现形"的那类。

---

## 几条沉淀下来的认知

1. **LLM-as-judge 有噪声，单次结果别当结论。**
   v2 与 v3 的 9.6 / 9.4 差异、以及 `rag-1` 在两轮间的波动，都落在主观判断范围内。
   要拿它做 CI 门禁，得跑多次取统计值，而不是看一次的数字。

2. **评测标准要写成"可判定"的。**
   "调用检索"听起来很明确，但 judge 仍可能按自己的理解去评。
   行为类标准必须锚定到客观事实（真实调用记录），不能让它从输出里反推。

3. **兜底逻辑会掩盖缺陷。**
   `synthesize` 让 Agent 在功能上"看起来能用"，分数也不难看，
   于是真正的多步缺陷被藏了很久。兜底要留，但要能在 trace 里看见它被触发。

4. **多入口工程的配置加载要下沉。**
   入口文件写 `import 'dotenv/config'` 是常见写法，但只要出现第二个入口就会漏。

5. **别给关键配置写"合理"的 fallback。**
   宁可直接报错，也不要静默用一个能跑但不对的值。

6. **"先让它跑起来"这件事，要留证据。**
   这个工程此前一直"以为完工"，是因为从没有人真正执行过 `npm run eval`。
   一个能跑的脚本，和一份**能复现的报告**，是两回事。
   现在每轮归档进 `docs/`，报告不再躺在被 gitignore 的临时文件里。
